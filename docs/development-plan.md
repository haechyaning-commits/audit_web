# 공공감사데이터 포트폴리오 — 개발 진행 계획 (WBS) v1

> 전제: `docs/architecture.md` v3 기준. 개인 프로젝트, 파트타임 진행을 가정한 대략적 소요일수 표기.
> 소요일은 "실제 작업 착수 후 얼마나 걸릴지"를 가늠하기 위한 러프 추정치이며, 리랭커·형태소 분석기처럼 처음 다루는 컴포넌트는 실제로 더 걸릴 수 있음.

## 1. 개발 순서를 정하는 원칙

1. **의존성 우선**: 배치 데이터 → DB 적재 → 검색/상세 API → 프론트엔드 순서로, 하위 계층이 준비되지 않으면 상위 계층은 목업 이상으로 진행할 수 없음
2. **리스크 게이트 우선**: 구조를 뒤흔들 수 있는 불확실성(임베딩+리랭커 동시 로드 메모리, 한국어 토큰화 효과)은 본 구현 전에 먼저 검증 — 나중에 걸리면 앞 단계 작업이 통째로 재작업될 수 있음
3. **품질 근거는 흐르면서 축적**: eval set 결과·ADR·성능 로그는 Phase5/6에서 몰아서 쓰는 게 아니라 각 Phase 산출물이 나올 때 바로 기록 (README 작성 시 재구성 비용을 줄임)

---

## 2. 전체 흐름

```
Phase 0  사전 검증 게이트 (리스크 해소)
   │
   ▼
Phase 1  배치 마무리 (임베딩 + 형태소 토큰화 + 4줄 요약) ── 내부적으로 병렬 가능
   │
   ▼
Phase 2  DB 스키마 확정 + pgvector 적재
   │
   ▼
Phase 3  검색 API / 상세 API 구현
   │
   ├──────────────┐
   ▼              ▼
Phase 4        Phase 5
프론트엔드      검색 품질 평가 (Phase3 완료 시점부터 병행 가능)
   │              │
   └──────┬───────┘
          ▼
Phase 6  배포 + 성능 실측 (NFR2 검증)
          │
          ▼
Phase 7  문서화 (README/ADR/회고 정리)
```

Phase 4(프론트)와 Phase 5(품질평가)는 서로 의존성이 없어 병렬 진행 가능 — 전체 일정의 병목이 아님.

## 4. 크리티컬 패스

```
Phase0 → Phase1 → Phase2 → Phase3 → Phase4 → Phase6 → Phase7
                                    ↘ Phase5 ↗ (병렬, 병목 아님)
```

일정이 밀릴 때 가장 먼저 확인해야 할 구간은 **Phase3(검색 API)** — 임베딩·토큰화·리랭커·캐시 4개 컴포넌트를 한 프로세스에 통합하는 단계라 실제로는 예상보다 오래 걸리는 경우가 많음. Phase0에서 메모리/토큰화 리스크를 먼저 걷어내는 이유도 Phase3에서 이중으로 발목 잡히지 않기 위함.

| 2. DB 적재 | 2일 | |

| 4. 프론트엔드 | 3~4일 | |
| 5. 품질 평가 | 2일 | Phase4와 병행 가능 |
| 6. 배포/성능 실측 | 1~2일 | |
| 7. 문서화 | 1~2일 | |
